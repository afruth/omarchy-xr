# Cursor capture investigation — 2026-09-20

The XR pointer ring has been removed. Capture now requests the compositor's native
cursor (`overlay_cursor=1`); gaze still selects workspaces only on halo transitions.

Two waits delayed capture delivery: copy requests generated by buffer negotiation
were not flushed immediately, and completed captures were consumed only at the
next rendered frame. Direct presentation now advances capture (including texture
updates and the next request) during the DRM page-flip wait. Everything remains on
the render thread, with the GL context current. The rendered scanout buffer is not
modified; updates prepare textures for the next draw. Measured CPU work includes
capture work during the wait. Phase-preserving capture deadlines tolerate 1 ms of
scheduling variation instead of repeatedly slipping a whole rendered frame.

Hardware probe: `make build/capture-timing`, then
`python3 tests/live_capture_timing.py`. One existing 1920×1080 headless output,
DMA-BUF GPU capture reduced to 480×270, controlled cursor motion, 60 fps request
limit, four seconds per phase. The regular XR renderer was stopped for this run.

| Polling strategy | Cursor included | Captures in 4 s | Capture interval p95 |
| --- | --- | ---: | ---: |
| During presentation waits | No | 238 | 18.77 ms |
| Only at rendered-frame boundaries | Yes | 60 | 66.73 ms |
| During presentation waits | Yes | 240 | 20.69 ms |

These compare scheduling strategies in the probe, not an exact benchmark of the
old production binary. They measure capture delivery, not physical input-to-photon
latency, and do not guarantee the same results with every layout or application.
Disabling damage-aware capture did not improve the earlier test and was reverted.
The production capture default and the saved layout on this machine are now 60 fps;
existing saved layouts elsewhere retain their chosen setting. The native cursor's
visible rate is limited by actual capture delivery and the physical display refresh.
